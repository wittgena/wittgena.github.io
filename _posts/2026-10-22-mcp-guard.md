# Taming Wild MCP Servers: Zero-Spawn HITL Locks and Stateless Yield in Python

As the Model Context Protocol (MCP) becomes the standard for connecting AI agents (Claude Code, Cursor, Zed) to external tools, most local and production setups rely on direct point-to-point pipes.
Connecting agents straight to third-party MCP servers (`@modelcontextprotocol/server-postgres`, `server-filesystem`, etc.) introduces two immediate operational risks. Standard MCP clients treat tool calls as fire-and-forget operations:

1. **Unapproved Destructive Execution:** An agent hallucinating a `DROP TABLE` or reading `prod_secrets` executes immediately because third-party MCP servers have no native concept of Human-in-the-Loop (HITL) governance.
2. **Retry-Induced State Corruption:** When a tool call hangs or times out, agents blindly retry, leading to duplicate database writes or orphaned subprocesses eating up host memory.

You shouldn't have to fork and rewrite third-party Node.js or Python MCP servers just to add an approval step. 

In our previous post, we shared how we built a deterministic LLM pipeline with VCR replay. Today, we’ll show how we extended that control plane to the tool layer: interposing an MCP Gateway that enforces Pre-Flight HITL Locks on unmodified third-party servers, holds stdio sandboxes at Zero-Spawn until approved, and verifies out-of-band approvals via Slack Socket Mode (`RFC-6238 TOTP` & `1-Click Buttons`).

---

## 1. The Core Problem: Bridging the Human Latency Gap

Putting a human in the loop of an autonomous agent breaks standard synchronous request lifecycles. An MCP client expects a tool execution response within seconds; a human engineer reviewing a Slack alert takes anywhere from 5 seconds to 5 minutes.

If your gateway simply blocks the thread or boots up the `npx` stdio subprocess while waiting for human approval, you expose the host to resource exhaustion (zombie processes) and inevitable HTTP client timeouts.

To solve this, our MCP Gateway (`fiber`) enforces three architectural invariants:
- **Zero-Code Interception**: Inspect incoming JSON-RPC tool arguments at the gateway ingress using declarative regex traps—locking down any off-the-shelf MCP package without touching its source code.
- **Zero-Spawn Parking (`HTTP 202 Yield`):** Intercept high-risk payloads *before* worker I/O. If a call is trapped, the underlying stdio sandbox is not even booted (`active_sandboxes=0`), and the transaction yields statelessly via `HTTP 202 Accepted`.
- **Idempotent Lineage (PTA):** Every tool invocation is mapped to a deterministic transaction handle backed by a Phase Transition Anchor (PTA). If the client retries while the human is still reviewing on Slack, the gateway absorbs the retry without double-spawning the tool.

## 2. Zero-Code Onboarding: Declarative Pre-Flight Traps

Instead of manually supervising fragmented MCP processes, Fiber scans your existing `.mcp.json` or `.cursor/mcp.json` and mounts them onto a unified Tunnel Bus (`/v1/mcp-gateway/invoke`).

To guard a third-party server, you attach a pre-flight regex pattern via environment variables or the `fiber connect` CLI. Fiber supports two attestation modes:
1. **Default Mode (6-Digit RFC-6238 TOTP):** Requires a 6-digit TOTP code from an enrolled admin's authenticator app.
3. **Button Mode (`button:<regex>`):** Renders 1-Click Approve/Reject buttons in Slack for quick confirmation.

### Via Agent Config (`.mcp.json`)

```json
{
  "mcpServers": {
    "fiber-gateway": {
      "url": "http://127.0.0.1:8356/v1/mcp-gateway/invoke"
    },
    "repomix": {
      "command": "npx",
      "args": ["-y", "repomix", "--mcp"],
      "env": {
        "FIBER_PREFLIGHT_PATTERN": "button:DROP|TRUNCATE|DELETE"
      }
    }
  }
}

```

### Via On-Demand CLI Sidecar (`fiber connect`)

```bash
# 1. Provision local Ed25519 node keys & enroll Admin TOTP (renders terminal QR code)
$ fiber sign init
$ fiber sign enroll -u fiber

# 2. Network/Multiplex MCP with 6-Digit TOTP Pre-Flight Lock (Default)
$ fiber connect -t net-context7 -e https://mcp.context7.com/mcp -p "RESTRICTED_TOPIC|DROP"

# 3. Ephemeral Stdio MCP with 1-Click Slack Button Lock ('button:' prefix)
$ fiber connect -t local-fs -e "npx -y @modelcontextprotocol/server-filesystem /tmp" -p "button:prod_secrets|DELETE"
```

When a safe payload arrives (e.g., reading `public_readme.txt`), the Pre-Flight Guard evaluates the regex in sub-milliseconds and passes the request through with zero overhead.

### Mode B: Ephemeral Stdio + Zero-Spawn 1-Click Resume

For local stdio tools (like `@modelcontextprotocol/server-filesystem`), process lifecycle management is equally important. If an agent tries to execute `read_file` on `prod_secrets`, the npx subprocess shouldn't sit idle in memory while waiting for human input.
