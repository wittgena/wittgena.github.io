# Taming Wild MCP Servers: Zero-Code HITL Locks and Stateless Yield in Python

As the Model Context Protocol (MCP) becomes the standard for connecting AI agents (Claude Code, Cursor, Zed) to external tools, most local and production setups still rely on direct point-to-point pipes.
Connecting agents straight to third-party MCP servers (`@modelcontextprotocol/server-postgres`, `server-filesystem`, etc.) or internal financial daemons introduces two immediate operational risks. Standard MCP clients treat tool calls as fire-and-forget operations:

1. **Unapproved Destructive Execution:** An agent hallucinating a `DROP TABLE`, reading `prod_secrets.env`, or submitting an unverified financial order executes immediately because standard MCP servers have no native concept of Human-in-the-Loop (HITL) governance.
2. **Retry-Induced State Corruption & Resource Exhaustion:** When a tool call hangs waiting for approval or times out, agents blindly retry—leading to duplicate state mutations or orphaned `npx` subprocesses eating up host memory.

You shouldn't have to fork and rewrite third-party Node.js or Python MCP packages just to add an approval step.

In our previous post, we shared how we built a deterministic LLM pipeline with VCR replay. Today, we’ll show how we extended that control plane to the tool layer: interposing an MCP Gateway (`fiber`) that enforces declarative Pre-Flight HITL Locks on unmodified third-party and built-in servers, hot-reloads security rules via a canonical config (`~/.anchor/mcp.json`), holds ephemeral stdio sandboxes at Zero-Spawn until approved, and verifies out-of-band approvals via Slack Socket Mode (`RFC-6238 TOTP` & `1-Click Buttons`).

---

## 1. The Core Problem: Bridging the Human Latency Gap

Putting a human in the loop of an autonomous agent breaks standard synchronous request lifecycles. An MCP client expects a tool execution response within seconds; a human engineer reviewing a Slack alert takes anywhere from 5 seconds to 5 minutes.

If your gateway blocks the thread or boots up the `npx` stdio subprocess while waiting for human approval, you expose the host to zombie processes and inevitable HTTP client timeouts.

To solve this, Fiber's MCP Gateway enforces three architectural invariants:
- **Zero-Code Pre-Flight Interception:** Inspect incoming JSON-RPC tool arguments at the gateway ingress using declarative regex traps (`FIBER_PREFLIGHT_PATTERN`)—locking down any off-the-shelf MCP package or persistent daemon without touching its source code.
- **Stateless Yield (`HTTP 202`) & Zero-Spawn Parking:** Intercept high-risk payloads *before* worker I/O. On persistent daemons, this guarantees **Zero-I/O** prior to approval; on ephemeral stdio tools, the underlying `npx` subprocess is not even booted while the request waits statelessly via `HTTP 202 Accepted`.
- **Idempotent Lineage (PTA):** Every tool invocation is mapped to a deterministic transaction handle backed by a stateful transaction ledger. When the client polls or retries with the same idempotency key after human approval, the gateway resolves directly from the ledger (`Existing state found: RESOLVED`) without double-executing the tool.

## 2. Declarative Onboarding: `fiber connect copy` & Hot-Reloading

Instead of manually supervising fragmented MCP processes across different IDEs, Fiber centralizes tool governance into a single canonical config: **`~/.anchor/mcp.json`**.

Using `fiber connect copy`, Fiber automatically scans your existing IDE configs (`.mcp.json`, `.cursor/mcp.json`) alongside built-in workers, normalizing their execution modes (`linear`, `multiplex`, `ephemeral`) and pre-flight security rules in one place.

Fiber supports two pre-flight approval modes out of the box:
1. **Default Mode (6-Digit RFC-6238 TOTP):** Requires a 6-digit TOTP code from an enrolled admin's authenticator app. Ideal for financial transactions or production mutations.
2. **Button Mode (`button:<regex>`):** Renders 1-Click Approve/Reject buttons in Slack for rapid developer confirmation on local stdio sandboxes.

### Step 1: Lock Targets into Canonical Config (`fiber connect copy`)

Rather than spawning ad-hoc foreground processes, you use `fiber connect copy` to register target servers and pre-flight regex traps directly into `~/.anchor/mcp.json`:

```bash
# 1. Provision local Ed25519 node keys & enroll Admin TOTP (renders terminal QR code)
$ fiber sign init
$ fiber sign enroll -u fiber

# 2. Scan existing IDE configs (.mcp.json / .cursor/mcp.json) + built-ins into ~/.anchor/mcp.json
$ fiber connect copy

# 3. Lock a built-in persistent daemon (worker.eco.finlib) with a 6-Digit TOTP Pre-Flight Guard
$ fiber connect copy -t worker.eco.finlib -e finlib -m linear -p "normalize_order|pow\(|exp\("

# 4. Lock a 3rd-party Ephemeral Stdio MCP with a 1-Click Slack Button Guard ('button:' prefix)
$ fiber connect copy -t hitl-stdio-fs-01 \
    -e "npx -y @modelcontextprotocol/server-filesystem /tmp/sandbox" \
    -p "button:prod_secrets|DELETE|DROP"

```

Running `fiber connect copy` produces a clean, canonical entry in `~/.anchor/mcp.json`:

```json
{
  "mcpServers": {
    "worker.eco.finlib": {
      "command": "/usr/local/bin/python3",
      "args": ["-m", "fiber.infra.mcp.worker.eco.finlib"],
      "env": {
        "FIBER_MODE": "linear",
        "FIBER_PREFLIGHT_PATTERN": "normalize_order|pow\\(|exp\\("
      }
    },
    "hitl-stdio-fs-01": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "/tmp/sandbox"],
      "env": {
        "FIBER_MODE": "ephemeral",
        "FIBER_PREFLIGHT_PATTERN": "button:prod_secrets|DELETE|DROP"
      }
    }
  }
}
```

### Step 2: Zero-Downtime Hot-Reload (`fiber daemon`)

When `fiber daemon` is running in the background, you never need to restart the gateway to apply new security rules. Whenever `fiber connect copy` updates `~/.anchor/mcp.json`, the daemon automatically detects the change and hot-reloads only the modified MCP servers with zero downtime.

```bash
# Production Mode: Automatically boots and hot-reloads all targets in ~/.anchor/mcp.json
$ fiber daemon -s all -f .env

# Standalone Mode (Optional): Omit 'copy' to run a specific worker directly in the foreground
$ fiber connect -t prod-db -e "npx -y @modelcontextprotocol/server-postgres" -p "DROP|DELETE"
```

### Phase 4: 3rd-Party Ephemeral Stdio + Zero-Spawn 1-Click Resume (`hitl-stdio-fs-01`)

For third-party stdio packages like `@modelcontextprotocol/server-filesystem`, process lifecycle isolation is paramount. When the agent attempts to invoke `read_file` on `prod_secrets.env`, the Pre-Flight Guard intercepts the call (`matched 'prod_secrets'`) and parks `txn_1792771875_3d5e9e31f62c` with `HTTP 202 Accepted`.

Because the request is intercepted at the gateway ingress prior to transport execution, the transaction is held purely in the control plane—consuming **zero OS processes** (`Zero-Spawn`) while waiting `43.0s` for the human operator to review the Slack alert.
