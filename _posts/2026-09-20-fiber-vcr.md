# Taming LLM Test Flakiness: Netty-Style Pipelines and VCR in Python

When building production-grade LLM agents, you inevitably hit a massive roadblock.

Your once-reliable CI/CD pipeline starts failing randomly due to external API latency, rate limits, or subtle model drift. When a test fails, root cause analysis becomes a nightmare—is it a regression in your internal business logic, or just a network hiccup from the LLM provider? This lack of isolation destroys Developer Experience (DevEx).

To solve this, we didn't rely on "better prompts" or introduce a flaky "LLM-as-a-judge." Instead, we decided to build a deterministic infrastructure boundary.

In this post, we’ll share how we ported a **Netty-style pipeline into Python** to decouple our logic, and how we leveraged it to build a flawless, offline **Record & Replay (VCR) environment** for our CI/CD pipelines.

---

## 1. The Core Problem: Tangled Logic and I/O

In the Python ecosystem, LLM API calls are usually implemented as giant monolithic wrappers. A single function handles prompt parsing, token budget management (billing), fallback logic, and the actual network I/O.

When you try to mock the network in this monolithic structure using traditional tools like `responses` or `unittest.mock`, you introduce a fatal side effect: you inadvertently bypass your own core business logic.
If you mock the entire function, your token counting or fallback routing logic is skipped. Your test environment no longer mirrors your production environment.

We realized we needed an architecture that strictly decouples our business logic from the physical network I/O.

---

## 2. The Architecture Shift: Porting the Pipeline Pattern

To manage this complex I/O lifecycle, we adopted the `ChannelPipeline` architecture—heavily inspired by Java’s Netty framework. We broke down the entire LLM request lifecycle into independent, pluggable lego blocks (`DuplexChannel`).

Here is a simplified look at how our pipeline is assembled:

```python
async def execute_completion(model, messages, **kwargs):
    pipeline = ChannelPipeline()
    
    # 1. Token budget checks & metadata binding
    pipeline.add_last(DphiFuelInterceptor())
    
    # 2. Prompt translation & Fallback routing
    pipeline.add_last(PayloadTranslator())
    pipeline.add_last(FallbackHandler())
    
    # 3. The actual network transport (The Boundary)
    pipeline.add_last(CompletionTransport()) 

    # Fire the request downstream through the pipeline
    return await pipeline.fire_channel_active(...)
```

The brilliance of this design lies in its directionality. Requests flow downstream, while responses and exceptions (errors) bubble upstream. Each channel only cares about its specific job and remains completely agnostic to the channels around it.

---

## 3. Perfect Synergy with Record & Replay (VCR)

This pipeline architecture truly shines when it's time to integrate our VCR engine.

Because our concerns are perfectly isolated, the VCR engine doesn't need to mutate the entire application flow. It simply swaps out the very last network block (`CompletionTransport` adapter) with an offline "Player."

```python
# Decoupled architecture: Storage manager & Network proxy
from fiber.dev.trace.llm.vcr.manager import VCRPlaybackConfig
from fiber.dev.trace.llm.vcr.proxy import VCRInjector

# The VCR injects itself globally, but only intercepts the bottom-most adapter.
# We apply a 100ms time-window (record_tick_ms) to coalesce fragmented stream chunks.
config = VCRPlaybackConfig(mode="replay", speed="real", record_tick_ms=100.0)
VCRInjector.apply(config=config, fixture_dir="./fixtures")

# Any acompletion call in CI will now read from local JSON fixtures.
# The VCR engine autonomously maps the request to the correct fixture 
# using deterministic metadata tunneling (e.g., vcr_scenario).
```

Because of this physical isolation, vital business channels like `PayloadTranslator` and `FallbackHandler` **execute exactly as they would in a live production environment.** The only difference is that when the final door (the network) opens, a pre-recorded JSON fixture responds instead of OpenAI, Anthropic, or your local inference server.

---

## 4. Restoring the Dimension of Time: Temporal Stream Emulation

Mocking static text payloads is only half the battle. In production, LLM agent crashes are rarely caused by the text itself—they are caused by asynchronous network timing (Time-to-First-Byte delays, backpressure, queue bottlenecks).

During the Record phase, our VCR engine captures more than just the payload. It records the exact millisecond latency between every single stream chunk (`delta_ms`) and the initial connection time (`ttfb_ms`).

```python
# A snippet from our VCR Replay engine (Temporal Emulation & Duck-Typing)
if config.speed == "real":
    await asyncio.sleep(metrics["ttfb_ms"] / 1000.0)

for coalesced_item in timeline:
    # Emulate the exact historical delay between time-windowed chunks (e.g., ~100ms)
    if config.speed == "real" and coalesced_item["delta_ms"] > 0:
        await asyncio.sleep(coalesced_item["delta_ms"] / 1000.0) 
        
    # The engine guarantees 100% duck-typing parity.
    # It yields a perfect mock instance, avoiding strict type-checking failures in legacy code.
    yield ModelResponseStream(
        choices=[{"delta": {"content": coalesced_item["chunk"]}}]
    )
```

Integrating this pipeline with our VCR engine boils down to one major win: **Reliable CI/CD.**

Running E2E tests in GitHub Actions is no longer a gamble against external API latency or rate limits. By pushing network calls to the edge and using offline fixtures, we eliminated test flakiness and billing costs.

Furthermore, you gain absolute control over time. While `speed="real"` is perfect for brutal timeout resilience testing (artificially injecting 502 Bad Gateway errors or massive latencies to stress-test the `FallbackHandler`), in our daily CI/CD pipelines, we run the VCR at `speed="max"` to instantly validate logic without waiting for network delays.

Consequently, when a pipeline fails today, the noise of provider fluctuations is gone—we know immediately the regression is strictly in our own code.
